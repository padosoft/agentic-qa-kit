# Agentic QA Kit — Enterprise implementation plan

This is the contributor-facing index for the complete roadmap. The detailed
maintainer blueprint remains in
[`docs/internal/implementation-plan.md`](internal/implementation-plan.md).
That document is the canonical source for the original Italian task
definitions, acceptance criteria, ADR references, and execution protocol.

## Product outcome

Agentic QA Kit is an agentic QA operating system, not only a test runner. A
production deployment must be deterministic where evidence matters,
sandboxed by default, observable, auditable, tenant-safe, cost-governed, and
able to use either hosted or private model providers.

## Delivery tracks

| Track | Scope | Current evidence |
|---|---|---|
| Foundations | schemas, CLI, runner, replay, storage, event chain | Implemented; verify with repository gates and journey tests |
| Enterprise packs | commerce, API, security, compliance, data, infra, mobile, desktop and specialist baselines | Pack directories are schema-validated and bundled; operator/runtime evidence remains pack-specific |
| Determinism | risk maps, invariants, bounded probes, replay and fix verification | Implemented in runner/store; external-provider evidence is separate |
| Governance | budgets, distributed reservations, kill switch, audit and redaction | Implemented at adapter/ledger/API boundaries; full deployment wiring and financial reconciliation remain acceptance items |
| Control plane | Postgres, OIDC/RBAC, admin editing, queues and runner leases | Implemented across packages; complete-journey and multi-replica evidence is required before production sign-off |
| Deployment | hardened OCI sandbox, Helm, Terraform and air-gap installation | Artifacts and gates exist; live cluster, registry, signature and recovery evidence must be supplied per environment |
| Assurance | SOC2/ISO mapping, threat model, pen-test scope, DR/RTO/RPO | Documentation and control catalog exist; independent operational evidence is not generated by local tests |

## Definition of done

A roadmap item is complete only when the implementation, unit/integration
tests, documentation and applicable build gates pass, and the representative
complete journey is proven against the real boundary it claims to cover:

`user/agent action → compiled interface or CLI → HTTP/API → durable state →
fresh authorized read/replay → denial and no side effect for an invalid
tenant/role/session`.

Fixtures, synthetic provider responses, a successful HTTP 200, a build, or a
test named E2E are not by themselves proof of a deployed production journey.
External provider, cluster, registry, payment, identity and disaster-recovery
evidence must be recorded separately and must never contain credentials.
